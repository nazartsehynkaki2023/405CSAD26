# Архітектура Build Engineer

## Зв'язки компонентів

```text
Build Engineer manifest
        |
        +--> prompt commands
        |       +--> git-init
        |       +--> create-project --> project-scaffold skill
        |       +--> create-build   --> build-and-test skill
        |       +--> create-actions --> github-actions skill
        |       +--> check
        |       `--> init (оркестратор)
        |
        `--> final check and report
```

Маніфест [build-engineer.agent.md](../.github/agents/build-engineer.agent.md)
визначає роль, доступні інструменти, skills, порядок і обмеження.
Prompt-файли є інструкціями для агента, а не shell-командами. Skills містять
повторювані процедури з входами, виходами та перевірками.

## Послідовність `/init`

1. Перевірити Python, Git, гілку та чистоту/конфлікти робочого дерева.
2. На `develop` створити `feature/develop/python-project`; якщо вона вже
   активна, продовжити в ній.
3. Виконати Git-підготовку.
4. Створити Python-структуру через `project-scaffold`.
5. Підготувати `.venv`, pytest і скрипти через `build-and-test`.
6. Створити matrix workflow через `github-actions`.
7. Виконати `/check` і лише після успіху сформувати звіт.

## Передавання даних

Кожен крок передає наступному корінь репозиторію, активну гілку, список
наявних/змінених файлів і результати попередніх перевірок. Skills не повинні
покладатися на поточний `PATH`: інтерпретатор і pytest запускаються з `.venv`.
Скрипти обчислюють корінь від власного розташування.

## Помилки та повторний запуск

Після помилки агент зупиняється на конкретному кроці й показує команду,
вивід та стан змін. Повторний запуск не перезаписує змінені користувачем
файли, не дублює конфігурацію й не створює зайвих гілок. Несумісні
frontmatter, workflow або гілка є конфліктом, а не приводом для мовчазного
відновлення. Push, PR, merge, reviewer, reset і rebase не виконуються.
